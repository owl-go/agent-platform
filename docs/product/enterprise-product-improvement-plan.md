# Agent Workspace 企业私有部署产品改进蓝图

状态：提案，尚未替代任何已批准产品规格

## 1. 结论与边界

### 1.1 第一阶段定位

Agent Workspace 第一阶段应定位为：

> 企业统一部署和治理、员工独立使用的个人 AI 工作台；帮助员工把一次成功的 AI 对话固化为可重复、可审计、可定时或通过 API 触发的 Workflow。

这个定位刻意区分三件事：

- 企业是采购、部署和治理主体，不等于“企业所有员工”是一个用户画像。
- 私有化部署、数据隔离和审计是采购准入条件，不是员工持续使用的理由。
- Session 是低门槛入口，Workflow 的重复执行才是留存闭环。

### 1.2 首批用户与任务

第一批设计伙伴优先选择企业研发、IT 运维或技术运营人员。原因不是这些人价值更高，而是当前产品已经具备 Runtime、Git Workspace、CLI Connector、文件产物和可审计执行的基础，离真实闭环最近。

首批只验证以下任务特征，不以“所有部门”作为范围：

- 每周至少重复一次；
- 输入和结果主要是数字化文件、代码、知识或系统数据；
- 当前人工处理超过三十分钟；
- 结果允许由用户复核后使用；
- 使用私有数据，公共消费级 AI 工具难以直接完成；
- 能客观判断成功、失败和节省时间。

财务等高风险岗位在结果准确性、审批、职责分离和审计能力形成证据前，不作为第一批自主执行用户。

### 1.3 第一阶段明确不做

- 不宣称企业协作平台；当前 User-owned 私有资源模型不足以支撑部门协作。
- 不新增顶层产品区域、Runtime 品牌、模型协议或第三方 Connector。
- 不把 Image Creation 作为默认导航或销售主张。
- 不建设任意 DAG、可视化编排器、应用市场或跨企业分享。
- 不为没有真实使用证据的功能增加复杂筛选、标签和管理字段。

### 1.4 北极星指标

北极星指标为：

> 每周至少成功执行两次的活跃 Workflow 数。

辅助指标：

- 首次登录到首次成功结果的中位时间小于 10 分钟；
- 新用户 24 小时内首次成功执行率不低于 70%；
- 成功 Session 到 Workflow 的转化率不低于 10%；
- 新 Workflow 30 天内至少执行两次的比例不低于 30%；
- 默认黄金路径端到端成功率不低于 95%；
- 设计伙伴核心任务相对原流程节省时间不低于 30%。

## 2. 产品角色与权限方案

第一阶段把购买、治理和使用职责分开，避免一个 Administrator 承担所有运营工作。

| 角色 | 核心目标 | 应有能力 | 不应有能力 |
|---|---|---|---|
| 部署管理员 | 安装、升级并保持平台可用 | 部署配置、备份恢复、系统健康、身份源、存储和 Runtime 配置 | 查看用户私有对话、提示词、文件和结果 |
| 平台管理员 | 管理可用模型、额度和平台资源 | 用户状态、模型目录、默认执行组合、平台 Expert/Skill/Connector、总量指标 | 查看用户私有执行内容或明文凭证 |
| 资源发布者（P2） | 发布部门可复用资源 | 创建和维护被授权范围内的 Knowledge Base、Expert、Skill 和 Workflow 模板 | 管理系统部署或其他部门资源 |
| 普通用户 | 完成个人任务并复用 | 私有 Session、Workflow、资源选择、历史和用量 | 查看其他用户内容或平台密钥 |

第一阶段仍可保持单企业实例，但应支持多个平台管理员，避免单一 bootstrap Administrator 成为运营瓶颈。部门、用户组和资源共享属于 P1 治理能力；在其完成前，界面和销售材料必须明确“用户私有 + 管理员发布平台资源”。

## 3. 信息架构与导航

### 3.1 用户端一级导航

| 新入口 | 包含内容 | 处理方式 |
|---|---|---|
| 首页 | 最近任务、待审批、失败恢复、常用 Workflow、新手引导 | 新增，作为登录默认页；未激活用户可直接开始首次任务 |
| 对话 | Sessions | 保留；文案强调探索和一次性任务 |
| 自动执行 | Workflows、Run Conversations、Artifacts、Workspace | 将 `Workflows` 改为任务导向文案，领域名仍保持 Workflow |
| 资源库 | Experts、Expert Teams、Skills、Connectors、Knowledge Bases | 合并当前分散入口；默认只展示可直接使用的资源 |
| 应用发布 | Smart Assistants | P1 默认隐藏；仅对已启用此能力的部署显示 |
| 设置 | 个人模型、语言、时区、个性与额度 | 保留，但将基础项与高级项分层 |

Image Creation 不进入第一阶段默认一级或二级导航。已部署能力可通过 Feature Flag 保留，入口标记为“实验功能”，不得与已验证主路径同等展示。

### 3.2 管理端导航

管理端从头像菜单进入独立控制台，避免普通用户设置与企业治理混杂：

1. 系统概览；
2. 用户与用户组；
3. 模型与 Runtime；
4. 平台资源；
5. Connector 与授权健康；
6. 用量与预算；
7. 审计与生产证据；
8. 部署设置。

### 3.3 全局交互规则

- 每个页面只有一个主要动作；创建、运行和发送不能同时竞争视觉焦点。
- 空状态必须解释“这个对象解决什么任务”，并提供一个直接动作，不展示纯技术定义。
- 状态统一使用 `未配置 / 可用 / 运行中 / 等待操作 / 失败 / 已停用`；技术状态放进详情。
- 所有失败必须包含：发生阶段、用户可执行的恢复动作、是否产生 Credits、输入是否保留。
- 删除、撤销授权、重新生成凭证等不可逆动作显示影响对象和后果，不使用泛化“确认删除”。
- 页面保留用户输入；只有后端接受成功后才清理草稿。
- 高级配置默认折叠，但折叠标题必须显示是否已配置和是否存在错误。
- 移动端提供完整审批、停止和失败恢复；复杂资源编辑允许提示使用桌面端，不伪装为完整可用。

## 4. 首次使用与首页

### 4.1 管理员部署向导

| 步骤 | 改进方案 | 完成标准 |
|---|---|---|
| 环境检查 | 自动检查 PostgreSQL、Object Store、Keycloak、Worker、Runtime、网络和时钟；按阻塞与警告分组 | 所有阻塞项通过，报告可下载且不含 Secret |
| 身份配置 | 默认接企业 OIDC；本地临时密码只作为应急路径 | 使用企业账号成功登录并完成退出、禁用验证 |
| 默认模型 | 管理员只需完成一个 Provider Connection、一个 Provider Model 和一个 Runtime 的黄金组合 | 执行真实测试并保存模型、Runtime Digest、时间和结果 |
| 平台资源 | 提供零个或最多三个经过验证的起始模板，不强制先建 Expert | 新用户无需额外配置即可运行首个任务 |
| 邀请试点用户 | 按名单或用户组开放，显示试点范围 | 用户能登录，管理员不能查看其私有内容 |

部署向导不得在基础闭环未完成时推荐图片模型或更多 Connector。

### 4.2 普通用户首次使用

1. 登录后进入首页，不先进入设置。
2. 首页用三个具体起始任务代替产品对象介绍，例如“分析一份文件”“处理一个代码库”“创建一个重复任务”。
3. 平台默认执行组合已可用时，用户无需理解 Provider Model 或 Runtime Engine。
4. 用户提交首个任务后直接进入 Session，显示预计会使用的资源和数据范围。
5. 首次成功结果下方只突出“继续追问”和“保存为自动执行”两个动作。
6. 首次失败保留输入，并提供“重试”“更换可用默认模型”或“联系管理员”，不能只显示错误码。

### 4.3 首页细节

- `继续处理`：最多五个最近 Session 或 Run Conversation，显示最后结果和待处理状态。
- `自动执行`：最多五个常用 Workflow，显示下一次计划时间、最近成功率和运行按钮。
- `需要你处理`：Connector 授权、高风险命令审批、额度不足和失败恢复。
- `开始新任务`：创建 Session；模板是可选快捷方式，不先要求选择 Expert。
- `系统提示`：只显示影响执行的事项，如默认模型不可用；不展示普通发布公告。
- 新用户空状态不展示八类产品功能，不使用轮播教学。

## 5. Sessions 改进方案

### 5.1 Session 列表

| 细节 | 方案 | 指标 |
|---|---|---|
| 新建 | 固定为列表顶部唯一主要动作；点击后立即创建空 Session | 新建到发送率不低于 80% |
| 标题 | 首条消息本地生成，可直接重命名；标题不占用模型调用 | 重命名失败率低于 1% |
| 列表信息 | 显示标题、最后更新时间、最后状态、选用的 Specialist；不展示内部 Run ID | 目标 Session 查找成功率不低于 90% |
| 搜索 | P1 支持标题和用户消息全文搜索；结果不跨用户 | 搜索后打开率不低于 40% |
| 归档 | 从活跃列表移除，归档页可恢复；归档后只读 | 误删除反馈为零 |
| 删除 | 明确删除消息、文件引用和执行数据；有活动执行时先停止 | 删除冲突有明确恢复动作 |

### 5.2 Composer

| 细节 | 方案 | 指标 |
|---|---|---|
| 默认状态 | 只显示输入框、附件和发送；Expert、Skill、Connector 收进 `+` | 首次用户不打开资源菜单也能完成任务 |
| Specialist | 统一显示“无专家 / 专家 / 专家团队”；解释 Expert 改变工作方法，不改变模型 | 错误选择后立即切换比例低于 15% |
| Skill | `/` 和 `+` 使用同一目录；Skill Token 标明仅本次消息生效 | 用户能正确预测作用范围的比例不低于 80% |
| Connector | 选择和启用分开；未授权时在当前对话就地恢复 | 授权成功后返回原任务比例不低于 80% |
| 文件 | 支持选择、粘贴、历史 Artifact 和 Workflow Workspace 文件；提交前展示来源与大小 | 文件作用域错误率低于 1% |
| 草稿 | 按 User 和会话保存文本、选择和已上传文件引用；未上传本地文件提示重新选择 | 导航返回后的草稿恢复率 100% |
| 发送 | Enter 发送、Shift+Enter 换行；中文输入法确认不触发发送 | IME 误发送为零 |
| 停止 | 生成中发送按钮变停止按钮；停止后说明已产生的消耗 | 停止请求可见反馈小于 1 秒 |

### 5.3 回复与执行状态

- 回复区先展示最终内容，执行活动默认折叠；不得让 Runtime 日志压过结果。
- 进行中显示当前阶段、已耗时和停止操作，不显示伪造完成百分比。
- Expert Team 显示“第 N/M 个角色正在处理”，提交前显示预计调用次数和 Credits 区间。
- 失败回复保留已产生的安全部分输出，区分配置失败、资源不可用、模型失败、授权等待、取消和额度不足。
- Retry 严格复用历史输入和资源快照；“复制并修改”创建新草稿，两者文案不能混用。
- 每个成功回复提供复制、评价、查看资源、查看消耗、保存为 Workflow；文件 Artifact 紧跟回复展示。
- 评价只收集 `解决 / 部分解决 / 未解决`，未解决时追加一个可选原因，不弹出长问卷。

### 5.4 Session 转 Workflow

`保存为自动执行` 是核心增长动作：

1. 从成功回复、用户原始输入和当前选择预填 Workflow 名称与目标；
2. 自动带入 Specialist、Skills、Connectors 和文件来源，但要求用户确认动态文件是否应改为 Knowledge Base 或 Workspace；
3. 默认创建手动 Workflow，不强迫配置 Schedule、API、Git 或环境变量；
4. 创建完成后立即执行一次验证 Run；
5. 验证成功后再询问是否设置周期；
6. 原 Session 与新 Workflow 互相记录来源链接，但不共享后续历史。

### 5.5 执行证据，而不是暴露内部推理

当前会话已经能展示准备 Runtime、Reasoning Summary、命令、文件变化和 Expert Stage，但这些活动仍不足以证明最终回答实际使用了什么依据。改进目标不是展示更多原始日志或 Chain-of-Thought，而是形成平台可验证的执行证据。

每个 Assistant Turn 增加折叠的 `本次执行`摘要：

- `依据`：实际读取或检索成功的附件、File Reference、Knowledge Citation 和外部数据源；
- `工具`：实际开始的 Connector 或受控命令、完成状态和安全动作摘要；
- `文件`：实际新增、修改并最终保留的文件，以及失败或取消后丢弃的变化；
- `阶段`：Expert Team 成员位置、状态和耗时；
- `消耗`：模型调用次数、最终 Credits 和是否存在未开始的阶段。

证据必须由平台事件、Retrieval Citation、Connector Broker 和 Artifact 捕获结果生成，不能由模型在最终回答中自行声明。资源状态至少区分：

```text
可用但未调用 -> 已调用 -> 调用成功并用于结果
                    └-> 调用失败或结果未采用
```

最终回答中的 `本次依据`只链接平台确认的记录；没有证据时明确显示“未使用外部资料或工具”，不能根据回答文字猜测。默认只显示摘要，用户展开后查看安全命令摘要、来源和失败原因；原始 Tool Output、Secret、完整敏感输入和私有 Reasoning 永不展示。

验收标准：

- 任一声称使用 Connector、Knowledge Base 或文件的结果，都能对应至少一条成功执行证据；
- 未调用的可用资源不得出现在“已使用”列表；
- 失败和取消路径不把临时文件变化标记为最终结果；
- 用户测试中至少 80% 的参与者能判断回答是否实际使用了指定资料；
- 因“是否真的调用工具”产生的试点反馈低于相关执行的 5%。

### 5.6 条件式计划确认

不为每条消息增加 Plan。简单问答先生成计划只会增加等待和 Credits。计划确认仅在以下任一条件成立时触发：

- 用户显式选择 `先制定计划`；
- 预计包含多个可独立判断的步骤；
- 需要调用两个以上外部工具或数据源；
- 可能修改文件、发送消息或产生其他外部副作用；
- Expert Team、长时间 Workflow 化任务或高风险命令即将参与；
- 系统预计任务超过一分钟，但无法在提交前安全确定结果。

计划卡显示：目标复述、步骤、拟使用的资源、外部副作用、需要确认的节点和预计模型调用次数。操作为：

- `开始执行`：冻结当前计划并开始；
- `编辑要求`：把修改作为新的用户输入重新生成计划，不直接修改隐藏模型状态；
- `直接回答`：仅在没有外部副作用时跳过计划；
- `取消`：保留原始草稿，不产生正式执行。

执行中按冻结计划显示步骤状态 `待开始 / 进行中 / 完成 / 跳过 / 失败`。Agent 可以因新证据提出变更，但新增外部副作用或扩大数据范围必须再次确认。计划不是正确性保证，也不能代替高风险命令的一次性审批。

验收标准：

- 普通单轮问答不出现计划卡；
- 涉及外部写操作的任务 100% 在第一次副作用前展示计划或明确审批；
- 长任务因方向理解错误而在执行一分钟后被停止的比例下降 30%；
- 计划确认到正式开始的中位时间低于 20 秒；
- 计划生成本身的 Credits 和失败必须可见，不能伪装成免费前端交互。

### 5.7 自适应会话工作区

正文宽度使用可读字符宽度而不是只写死像素：Assistant 正文目标为 `68ch–76ch`，代码块和表格可以在内容区内横向滚动。当前桌面实现已经把消息限制在 820px，不能继续用“整屏 100+ 字符”描述现状；需要通过真实浏览器和中英文内容验证实际行长。

右侧不永久放一个空面板。只有当前 Turn 存在计划、执行证据、来源、文件或 Artifact 时，在宽屏桌面展示可折叠的 `任务面板`：

1. `计划`：冻结步骤和当前状态；
2. `依据`：实际使用的文件、Knowledge Citation 和 Connector 数据源；
3. `文件`：附件、生成文件和 Artifact；
4. `结果摘要`：完成状态、耗时、Credits 和保存为 Workflow。

布局规则：

- 视口不小于 1280px 且存在面板内容时，正文保持约 720–780px，面板约 320–380px；
- 没有面板内容时保持居中的单列会话，不为“利用空间”制造空白组件；
- 窄屏桌面和平板使用右侧 Drawer；移动端使用底部全屏 Sheet；
- 选择历史 Turn 时，面板切换到该 Turn 的证据与文件，不混用最新执行状态；
- 面板折叠状态按用户和设备保存，不进入业务快照。

验收标准：中英文长回答的正文行长落入目标范围；1280px、1440px、1920px 和 390px 视口均无水平页面滚动；面板关闭后正文不会被强制拉宽。

### 5.8 持续可见的状态与控制条

当前状态、Activity、停止按钮、耗时和最终 Credits 已存在，但分别散落在 Assistant 消息、Composer 和结果底部。长任务需要一个位于 Composer 上方、始终可见的状态控制条。

运行中控制条显示：

- 公开状态：`排队中 / 准备中 / 执行中 / 等待你操作 / 正在整理结果`；
- 已耗时；
- 当前步骤或 Expert Team 位置；
- 当前安全活动摘要，例如“正在检索知识库”或“正在等待 Connector 授权”；
- 已发生的模型调用次数；实时 Token 或 Credits 不可靠时明确显示“完成后结算”，不得展示猜测值；
- 主操作：排队时为`取消排队`，运行时为`停止`，等待时为对应审批或授权动作。

终态在结果头部展示明确 Badge：`已完成 / 部分完成 / 失败 / 已停止`。失败旁边直接提供 Retry、修复资源、补授权或联系管理员；完成后状态条收起为结果摘要，不长期占据输入区域。

刷新、网络重连和浏览器从后台恢复时，客户端先读取权威状态，再恢复事件流。超过十秒没有新活动时显示“任务仍在运行，最后更新于……”，不能继续播放假动画让用户误以为有进展。

验收标准：

- 活动任务的状态和停止入口在任意滚动位置都可见；
- 停止点击后一秒内出现已接收反馈，最终状态来自服务端；
- 重连后不重复显示 Activity、不丢失终态、不误报完成；
- 100% 的终态结果显示状态、耗时和 Credits outcome；
- 用户测试中将长任务误认为页面卡死的比例低于 5%。

## 6. Workflows 改进方案

### 6.1 Workflow 列表

| 细节 | 方案 |
|---|---|
| 卡片 | 显示名称、用途摘要、最近一次状态、30 天成功率、下次计划时间和运行按钮 |
| 状态筛选 | 默认 `全部 / 需要处理 / 计划中 / 已停用`；技术运行状态放详情 |
| 创建入口 | `从成功对话创建`为推荐路径；`从空白创建`和`从模板创建`为次级路径 |
| 运行 | 点击运行立即创建 Run Conversation 并打开，不让用户去历史页寻找 |
| 批量操作 | P0 不做批量运行和删除，避免误操作 |
| 删除 | 显示将删除的配置、Workspace、凭证和 Schedule，以及保留的历史与 Artifact 元数据 |

### 6.2 创建流程

创建拆成最小主流程和按需高级配置：

1. 必填名称和目标；
2. 可选选择一个 Expert 或 Expert Team；
3. 创建后直接运行验证；
4. 验证成功后再配置 Knowledge Base、Schedule、API、Git 和环境变量；
5. 每增加一项配置都提供“测试当前配置”，不等到正式 Run 才发现错误。

不得在初始弹窗同时展示全部 Knowledge Base 和基础设施字段。资源很多时使用搜索选择器，不铺满复选框。

### 6.3 Workflow 详情

详情页调整为：

1. `概览`：目标、最近状态、成功率、下次计划时间、运行按钮和待处理事项；
2. `对话与运行`：按 Run Conversation 展示完整上下文；
3. `结果文件`：Artifacts；
4. `工作目录`：Workspace；
5. `设置`：基础、资源、触发、环境、API 和 Git。

当前以 Artifacts 为第一个 Tab 的结构不适合作为默认落点，因为没有运行过的 Workflow 会直接进入空页面。

### 6.4 手动、计划与 API 触发

| 触发方式 | 改进方案 | 异常处理 |
|---|---|---|
| 手动 | 直接执行固定目标；运行前只展示关键资源和预计消耗 | 依赖不可用时不创建 Run，并跳到具体配置项 |
| Schedule | 保存前显示未来三次实际执行时间和时区 | 错过执行要保留失败记录，不静默补跑 |
| API | 生成凭证后提供可复制的最小请求、轮询和 SSE 示例 | 凭证只显示一次或明确说明可再次读取的安全语义 |
| Follow-up | 复用 Run Conversation 的冻结上下文和 Workspace | 明确不会修改 Workflow 默认配置 |
| Rerun | 原样复用失败 Run 的快照 | 若依赖已撤销，显示不可重跑原因并提供复制为新 Run |

### 6.5 Queue 与并发

- 运行按钮提交后立即显示队列位置，不重复点击创建多条 Run。
- 队列满时说明当前上限和可取消项；手动/API 不创建失败记录，Schedule 保留审计记录。
- User Action Wait 不占用普通执行超时，但必须显示剩余确认时间。
- 一个 Workflow 串行、不同 Workflow 并行的规则在首次出现排队时解释一次。
- 管理端只看聚合队列健康，不查看用户输入。

### 6.6 Schedule

- 默认关闭；开启后先选频率，再选时间和时区。
- 保存前显示未来三次运行时间，处理夏令时和时区变化。
- 提供暂停而不是要求删除 Schedule。
- 连续三次失败后暂停后续执行并通知用户，避免持续消耗与噪声。
- 用户禁用、模型不可用或额度不足时显示阻塞原因和恢复条件。

### 6.7 API Credential

- 默认不生成；首次开启时解释用途和权限范围。
- Key 和 Secret 的复制操作分别记录本地完成状态，不把明文写入日志或遥测。
- Regenerate 前展示旧 Token 会立即失效，并要求输入 Workflow 名称确认。
- 提供最后使用时间、最近失败数和主动停用操作。
- API 凭证不能审批高风险 Connector 命令，界面明确写出限制。

### 6.8 Environment 与 Git Source

- 普通变量支持显示、编辑和删除；Secret 只显示“已配置”和最后更新时间。
- 变量名即时校验并提示重复、保留名和无效格式。
- Git 配置用 `公共 HTTPS / HTTPS 凭证 / SSH 私钥` 三种明确模式，不先展示底层字段。
- Clone 前检查 Workspace 必须为空并给出可选处理方式，但不得自动清空。
- Clone 结果固定显示在保存操作附近，失败保留非 Secret 输入并清除不应持久化的 Secret。
- P0 不增加 Commit、Push、Branch Review 或 PR 流程。

## 7. Workspace、Artifacts 与运行历史

### 7.1 Workspace

- 初始空状态说明文件由成功 Run 或 Git Clone 产生，不能在此直接编辑。
- 文件树支持面包屑、名称排序和当前路径复制；P0 不做全文搜索。
- 文本预览显示大小限制和编码失败原因；二进制文件直接下载。
- 每个文件可查看“最后由哪个 Run 更新”，但不暴露 Runtime 临时路径。
- 接近 1 GB 配额时在 Workflow 概览提示；超限 Run 必须失败且丢弃临时变化。
- 成功合并、失败丢弃的规则在首次失败时解释，不需要长期占据页面。

### 7.2 Artifacts

- Artifact 只展示明确的最终交付物，不为普通文本结果制造伪文件。
- 文件卡显示名称、类型、大小、来源 Run、过期时间和下载。
- 多文件提供批量 ZIP 下载；ZIP 是临时下载，不产生新 Artifact。
- 过期后保留元数据并明确不可下载，不显示失效按钮。
- Session 和 Workflow 使用同一文件预览与下载体验。

### 7.3 Run History

- 一行代表一个 Run Conversation，而不是一个底层执行 Attempt。
- 列表显示触发方式、最后状态、累计耗时、最近更新时间和是否需要用户操作。
- 打开后进入完整对话视图；底层 Snapshot、Lease、Attempt 和 Runtime Event 只在受限诊断中使用。
- 失败项提供具体恢复动作：重跑、修复资源、补授权、补额度或联系管理员。
- 删除 Workflow 后历史只读，不显示任何可运行入口。

## 8. Experts 与 Expert Teams

### 8.1 Expert 目录

- 目录默认优先显示管理员发布且经过验证的平台 Expert，其次是我的 Expert。
- 卡片显示用途、适合的任务、Skill/Connector 数和最近验证状态，不显示模型与 Runtime。
- `召唤`直接打开新 Session 并预选 Expert；点击卡片只开详情，行为保持分离。
- 搜索覆盖名称、简介和派生标签；派生标签不能作为权威能力声明。
- 无 Expert 仍是默认可用路径，不能制造“必须先配专家”的错觉。

### 8.2 Expert 编辑

| 字段 | 改进方案 |
|---|---|
| 名称 | 用用户能识别的岗位或任务命名，不接受只有“助手”“专家”的低信息名称 |
| Introduction | 只解释适用任务和边界，不注入执行 |
| Core Capability | 用“能够处理什么输入并产出什么结果”的结构化提示引导填写 |
| Operating Procedure | 提供分步模板和预览，避免与 Workflow 概念混淆 |
| Output Standard | 要求明确格式、质量检查和引用要求 |
| Cautions | 提示准确性、权限和必须人工复核的场景 |
| Skills/Connectors | 展示来源、版本、权限和可用性；新建后自动选中 |

保存前提供一次测试对话，不要求先退出编辑页。Incomplete Expert 保留但不能被新任务选择，并直接定位缺失字段。

### 8.3 Expert Team

- 标记为高级能力，不在首次使用和默认资源推荐中出现。
- 创建前解释每轮会按成员顺序多次调用模型并分别消耗 Credits。
- Member 必须显示角色名、引用 Expert、标签、顺序和预计调用位置。
- 拖拽排序同时提供键盘上移/下移。
- 保存前执行结构校验：至少两名有效成员、无不可用资源、顺序完整。
- 运行失败采用 fail-fast；界面展示已完成成员、失败成员和未开始成员。
- 团队结果默认只展示最后成员正式回复，前序成员输出在执行详情中按需查看。

## 9. Skills 与 Connectors

### 9.1 Resource Center

- Skills、Connectors、Knowledge Bases 使用同一资源库外壳，但保持不同资源类型。
- 默认筛选为“可用”；草稿、失败、停用和不兼容资源进入状态筛选。
- 每张卡必须回答：它做什么、谁发布、会访问什么、在哪些 Runtime 可用。
- 平台资源与个人资源明确分组；P1 增加部门资源时必须显示作用范围。

### 9.2 Skills

- `去使用`打开新 Session 并预选 Skill，不自动发送消息。
- 详情安全渲染 `SKILL.md`，把内容当文档而不是平台指令。
- 安装支持 Git URL 和 ZIP；安装前显示来源、版本、文件清单和校验结果。
- 更新创建新 Revision，只影响未来明确选择；历史执行保持原 Revision。
- 删除前列出受影响的 mutable Experts，确认后解除引用但保留历史快照。
- `Create Skill` 会话式创建必须先展示完整草案和实际写入范围，再由用户确认。

### 9.3 MCP Connector

- 创建向导分为连接方式、地址或固定包、认证、Egress、测试五步。
- Test 必须展示成功能力列表和安全失败原因，不展示凭证明文与原始供应商响应。
- 未通过测试的 Connector 不能进入选择器。
- Credential 永远只显示“已配置”；更新时重新输入，取消时清空草稿。
- 删除或停用前列出受影响 Expert 和正在使用的会话选择。

### 9.4 CLI Connector 与授权

- 普通用户只浏览、安装、启用和授权管理员发布的版本，不能输入任意安装命令。
- 卡片显示包来源、版本、验证 Digest、支持能力、身份和风险摘要。
- 安装、连接外部账号、授权 Scope 是三个独立状态，界面不得合并成一个模糊开关。
- 缺失 Scope 时从当前任务发起最小授权，成功后回到原任务；不要求用户自己寻找管理页。
- 多账号授权必须显示当前选中的外部账号和 User/Bot 身份。
- Token 刷新失败后标记授权失效，不静默切换账号或身份。
- Disconnect 立即阻止未来调用，历史结果继续可读。

### 9.5 高风险命令审批

- 审批卡必须展示 Connector、执行身份、动作、目标、脱敏参数、请求来源和剩余时间。
- `批准一次 / 拒绝`是唯一动作，不提供永久放行。
- 批准绑定不可变 command digest 和 nonce；参数变化必须重新审批。
- 拒绝不一定取消整个执行，Runtime 可以给出低风险替代方案。
- Session、Run Conversation 和首页 `需要你处理`使用同一审批组件。
- Schedule/API 触发的审批必须进入站内待办；API Credential 永远不能代替用户同意。

## 10. Knowledge Bases

### 10.1 定位与入口

Knowledge Base 是供 Workflow 和 Smart Assistant 使用的资料源，不应作为普通用户首屏的独立目的。入口位于资源库，并从 Workflow 或 Assistant 的资源选择器直接创建或绑定。

### 10.2 创建与文档管理

- 创建只要求名称和用途说明；可见范围在 P0 只有“个人”或“平台”。
- 上传前展示支持格式、100 MiB 限制和数据将用于检索的说明。
- 上传接受与 Ingestion 完成分开；每个文档显示 accepted、processing、ready、failed 或 blocked。
- 失败保留源文件并提供重试；新 Revision 失败不替换最后可用 Revision。
- Category 只做单层管理，不伪装成文件夹或多级权限。
- URL 导入明确说明是一次性快照，不会自动持续同步。
- 删除提供 30 天恢复；永久清理由后台幂等执行。

### 10.3 检索验证

- Knowledge Base 详情提供测试查询，最多显示十条有来源的摘录。
- `未就绪 / 无匹配 / 检索失败 / 无权限`必须是四种不同状态。
- 每条结果展示文档、Revision、Category、摘录和相关性，不暴露内部向量。
- Workflow 或 Assistant 绑定前提示当前 Ready 文档数和最近一次成功索引时间。
- 无检索结果时不得默默假装使用了知识库；结果中明确说明是否有依据。

### 10.4 企业共享（P2 决策门）

只有完成用户组、部门范围、读写权限、离职转移和审计后，才能引入部门 Knowledge Base。不得用 Administrator 公共资源冒充部门协作。

## 11. Smart Assistants

Smart Assistant 从“通用 AI 应用”收窄为“把经过验证的问答能力发布给内部用户或受控外部访客”。在核心 Session → Workflow 闭环达标前默认隐藏。

### 11.1 目录与生命周期

- Draft、Enabled、Disabled 三态保留；不完整 Draft 不能开始新对话。
- 列表显示场景、受众、最近验证时间、绑定知识和分享状态。
- Copy 创建独立 Draft，不复制外部 Share Token 和历史对话。
- Enable 前运行发布检查：模型可用、FAQ 安全、Knowledge Ready、引用资源可用、额度策略明确。
- Disable 立即停止新对话，历史仍可读。
- Delete 显示历史保留和资源不会被删除的影响。

### 11.2 编辑器

- 基础信息、回答内容、知识与专家、对话外观、分享与限制分区展示。
- 先配置文本问答；非必要的展示配置不进入发布前置条件。
- 提供“以访客身份预览”，但预览不污染真实历史与用量统计。
- 每次保存显示配置 Revision；并发编辑使用明确冲突提示，不覆盖他人更改。

### 11.3 FAQ

- 支持新增、排序、启停、分类和 CSV 导入导出。
- 重复问题导入前预览替换清单，不直接覆盖。
- FAQ 点击直接返回存储答案，不调用模型、不检索、不扣 Credits。
- Markdown 统一安全渲染；启用前完成安全检查。
- 模型匹配必须保存 FAQ identity 和置信度，不能重写 FAQ 答案。

### 11.4 对话

- 首次打开创建或恢复最近 Assistant Conversation，不进入 Workspace Session。
- Welcome、FAQ 快捷项和输入框构成首屏，配置项不进入对话界面。
- 只允许一个生成中的 Turn；停止、失败和部分输出写入审计历史。
- 回答必须区分 FAQ、知识检索和模型直答来源。
- 没有足够检索依据时返回明确的无依据结果，不编造已引用来源。

### 11.5 分享与 iframe

- 默认关闭；开启前展示匿名访问、所有者付费和数据处理影响。
- Token 可立即轮换或撤销；旧 iframe 同时失效。
- allowed Origins 默认要求显式配置，生产环境不得用无限制作为推荐值。
- Free-text 和每日调用上限是必须配置项；FAQ 点击不计模型调用。
- 分享页不得暴露内部模型、Expert、Knowledge Base、User Token、Object Key 或签名 URL。
- 管理端只看聚合调用、错误和额度，不查看访客私有内容。

### 11.6 回答安全与来源

- 平台不可关闭的安全规则在 FAQ 匹配、Knowledge Retrieval 和模型调用之前执行。
- 拒绝只返回固定本地化文案，不暴露命中的规则、分类或敏感原文。
- FAQ 在启用前检查，Knowledge Document 在进入 Ready Index 前检查；阻断不能只发生在生成答案之后。
- 安全分类器若产生真实模型调用，必须计入所有者 Credits，并在结果中说明发生了计费检查。
- 只保存最小安全审计：Assistant、时间、访问来源、结果、策略版本和 Credit outcome；普通日志不保存完整敏感输入。
- FAQ 直答标识 `FAQ`，有依据的模型回答展示 Citation，无命中时明确标识“未使用知识库依据”。

## 12. Image Creation

处理决定：保留已实现能力，但默认放入实验功能，不作为核心留存链路。

若部署启用：

- 管理员必须先完成真实图片模型测试，未验证模型不能被用户选择；
- 用户提交前显示模型、数量、预计固定 Credits 和参数兼容性；
- Reference Image 上传明确说明原始字节及元数据会发送给 Provider；
- Prompt Optimization 是显式按钮；成功后替换当前草稿并只允许恢复上一个版本，不自动开始生成；
- 生成中锁定参数，只保留 Stop；离开页面后后台继续；
- succeeded、partially_succeeded、failed、cancelled、outcome_unknown 分别呈现，不混成“失败”；
- 只对已验证并持久化的图片结算；缺失位置展示安全失败原因；
- 一张结果使用大图，两至四张使用响应式网格；点击进入全屏预览并支持逐张下载；
- 批量下载生成临时 ZIP，不产生另一份 Generated Image；
- 历史按时间倒序分页，桌面折叠、移动端抽屉；P0 不增加搜索和筛选；
- Regenerate 使用原请求创建新 Record，Reuse settings 只回填草稿，两者不能混用；
- 90 天到期前七天提示下载，过期后保留元数据；
- 只允许删除完整的终态 Record，不能删除单张结果；活动 Record 必须先停止；
- 无持久草稿时，离开页面必须明确提醒未提交内容会丢失。

## 13. Credits 与企业用量治理

### 13.1 用户侧

- `Available Credit` 保留为执行准入值，但用户界面使用“可用额度”解释。
- Session、Workflow 和 Expert Team 提交前展示预计调用次数和额度区间。
- 结果后展示总消耗和按阶段摘要，不展示供应商成本与内部倍率。
- 失败、取消、超时分别解释是否产生消耗；Retry 是新的独立消耗。
- 额度不足提供下一次恢复时间和联系管理员入口，不建议普通用户使用 Redemption Code。

### 13.2 管理侧

- 私有化部署默认使用管理员分配额度，不把 Redemption Code 作为主流程。
- P0 支持平台默认和单用户额度；P1 在用户组模型建立后支持部门预算与告警。
- 管理员查看余额、当日用量、失败率和聚合模型消耗，但不能查看具体 Session、Workflow 或提示词。
- 预算达到 80% 时通知管理员和相关用户；达到 100% 后按策略阻止新执行。
- Credit Adjustment 必须有原因和不可变审计；不能直接覆盖余额。
- Model Credit Rate 作为内部治理配置放入高级管理，不要求普通用户理解。

### 13.3 Redemption Code

默认从企业部署 UI 隐藏。只有存在渠道分发或独立计费的明确商业需求时再启用；不能因为后端已经实现就占据普通用户的 Credit Panel。

## 14. Personal Settings

### 14.1 普通用户设置

| 分区 | 方案 |
|---|---|
| 执行默认值 | 默认继承平台黄金组合；高级用户才展开 Runtime 与 Provider Model |
| 个性 | 只控制沟通风格，提供即时示例，不暗示改变能力 |
| 语言与时区 | 语言即时切换；时区变更明确影响 Schedule 和下一 Credit Day |
| Connector 账号 | 展示已连接账号、身份、Scope、过期状态和断开操作 |
| 数据与隐私 | 展示私有资源边界、文件保留期、Session 删除影响和导出入口 |

普通用户设置不再管理 Skills、Connectors 包或平台 Model Catalog。

### 14.2 模型选择

- 首次用户不强迫选择模型；默认继承平台验证组合。
- 高级选择器先显示“推荐”，再显示其他 verified 组合；unverified 放入实验分组。
- incompatible 不能保存；unavailable 不静默回退。
- 切换明确说明只影响新 Session 和新 Run Conversation，历史不变化。

## 15. 管理控制台

### 15.1 用户管理

- 支持创建、禁用、启用、重置密码和查看最后登录；优先接企业身份源自动供应。
- 禁用前显示将取消运行、暂停 Schedule 和撤销 Workflow API 的影响。
- 多管理员操作必须有操作者、时间、目标和原因审计。
- P1 引入用户组时先支持只读身份源同步，避免在产品内维护第二套组织树。

### 15.2 模型与 Runtime

- Model Provider Connection、Provider Model、Runtime Engine 和 Compatibility 分层管理。
- 首页突出唯一推荐黄金组合及其最近真实验证时间。
- Endpoint、API Key、模型或 Runtime Digest 变化后自动回到 unverified。
- 未通过真实调用和 Conformance 的组合不能标为推荐或默认。
- 测试结果只保存安全元数据，不保留明文 Secret 和原始模型内容。

### 15.3 平台资源

- 管理员发布的 Expert、Skill、Connector 和 Knowledge Base 使用统一发布检查。
- 发布页显示 Revision、影响用户、兼容范围和回滚版本。
- 更新只影响未来明确选择，不重写历史快照。
- 资源停用前显示被多少 mutable Expert、Workflow 和 Assistant 引用，但不泄漏用户内容。

### 15.4 系统健康与审计

- 显示 API、Worker、队列、Object Store、OIDC、Runtime、Connector 和 Ingestion 聚合健康。
- 区分“配置存在”“本地测试通过”“真实 Provider 通过”“生产 Conformance 通过”。
- 告警只包含安全错误码、耗时、状态和 request identity，不包含提示词、文件、模型原文或 Secret。
- 支持导出管理员操作审计和生产证据清单，不导出用户私有内容。

## 16. 通知、待办与恢复

- 首页和全局顶部只保留一个待办入口。
- 待办类型限定为：命令审批、Connector 授权、额度不足、Schedule 连续失败、资源失效和管理员配置阻塞。
- 每条待办包含来源对象、发生时间、截止时间、主操作和忽略后果。
- 成功完成后自动从待办移除并返回原任务。
- 普通成功不进入待办；使用可自动消失 Toast。
- P0 不发送邮件或浏览器通知；只有站内通知闭环验证后再扩展渠道。

## 17. 产品数据方案

### 17.1 事件边界

遥测不得包含提示词、回复正文、文件名、文件内容、外部账号、API Key、Object Key 或签名 URL。事件只记录匿名 User、对象类型、入口、状态、耗时、错误分类和资源数量。

### 17.2 首次激活漏斗

| 事件 | 关键属性 |
|---|---|
| `login_completed` | identity_source、first_login |
| `default_execution_ready` | inherited、runtime_type、compatibility |
| `first_task_started` | entry、template_id、has_file |
| `first_response_succeeded` | duration_bucket、specialist_type、artifact_count |
| `first_response_failed` | failure_stage、safe_error_code、recoverable |
| `workflow_save_started` | source_session、prefilled_fields |
| `workflow_created` | source、has_schedule、has_connector |
| `workflow_second_run_succeeded` | days_since_create、trigger_type |

### 17.3 核心行为事件

- Session：创建、发送、停止、成功、失败、Retry、评价、归档、删除；
- Workflow：创建来源、验证 Run、运行、排队、触发方式、失败恢复、第二次成功；
- Resource：查看、选择、授权、测试、停用和不兼容；
- Knowledge：上传接受、Ready、失败、测试查询、绑定和命中；
- Approval：展示、批准、拒绝、过期和恢复；
- Credits：预计展示、额度不足和管理员调整，不记录用户内容。

### 17.4 上线仪表盘

只建立四张业务仪表盘：激活漏斗、Workflow 留存、黄金路径成功率、失败与恢复。没有形成明确决策的问题，不增加图表。

## 18. 分阶段实施计划

### P0：定位与黄金路径

范围：

- 确认研发/IT 设计伙伴和三个高频任务；
- 管理员部署向导与一个默认黄金模型组合；
- 普通用户首次使用直达 Session；
- 全量激活和失败阶段事件；
- 未验证 AI Applications 从默认导航隐藏；
- 所有失败提供可执行恢复动作。

退出标准：三家设计伙伴完成真实部署；24 小时首次成功率达到 70%；黄金路径成功率达到 95%。

### P1：Session 到 Workflow 留存闭环

范围：

- 成功回复一键保存为 Workflow；
- Workflow 概览和最小创建流程；
- 首次验证 Run 后再配置 Schedule/API/Git；
- Workflow 成功率、第二次运行和节省时间指标；
- 首页最近任务、常用 Workflow 与待办。

退出标准：Session 到 Workflow 转化率达到 10%；30 天二次运行率达到 30%；目标任务节省时间达到 30%。

### P2：企业治理

范围：

- 多管理员、资源发布者、用户组和只读身份源同步；
- 部门资源范围、预算、审计和离职转移；
- 平台资源发布与回滚；
- 聚合健康和生产证据控制台。

退出标准：管理员无需读取用户私有内容即可完成用户、资源、预算和故障治理；跨范围访问测试全部 fail closed。

### P3：受控应用发布

范围：Smart Assistant、FAQ、Knowledge grounding 和受控 iframe。Image Creation 继续独立按证据决定，不自动进入 P3。

进入条件：核心 Workflow 北极星指标连续四周稳定；至少三家设计伙伴明确提出发布型问答需求；外部访问的安全、成本和审计模型完成。

## 20. 需求验收模板

后续每个功能进入开发前必须回答以下问题，缺一项不得排期：

1. 它服务哪个角色和哪个高频任务？
2. 用户从哪里进入，完成后回到哪里？
3. 最小主流程需要几步，哪些字段可以延后？
4. 空状态、加载、部分成功、失败、取消、超时和权限不足分别如何呈现？
5. 输入是否保留，Retry 与复制修改的语义是什么？
6. 会读取、写入或向外发送哪些数据？
7. 谁能查看、修改、分享、停用和删除？
8. 是否产生 Credits，提交前后如何解释？
9. 哪个事件证明用户完成了任务？成功阈值是什么？
10. 哪些真实 Provider、浏览器、生产环境或 Conformance 证据仍缺失？

只有真实执行过的用户任务和生产证据可以改变功能的正式可用状态。规格完整、接口存在或单元测试通过都不能替代用户价值与生产闭环。
