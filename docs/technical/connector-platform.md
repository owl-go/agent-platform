# Connector Platform Contract

## Package validation

The package validator is the single boundary shared by ZIP upload and guided creation. It rejects empty or oversized archives, absolute or traversal paths, duplicate paths, symbolic links, hard-coded credential names or values, malformed JSON, missing required files, invalid semantic versions, and packages that declare both MCP and CLI manifests. A package must contain at least one `skills/<name>/SKILL.md`; every document must be UTF-8 with valid frontmatter and all referenced resources must stay inside that Skill directory.

The outer Connector Package ZIP still rejects symbolic links. Its nested immutable CLI bundle may contain only relative symlinks that resolve within the bundle, matching the CLI bundle extractor; absolute and escaping links fail validation. This permits the verified npm `.bin` links used by `@larksuite/cli` without weakening the outer package or Runtime mount boundary.

`connector-meta.json` owns the globally unique lower-case `source`, semantic `version`, package `type`, user-facing name and description, examples, platform compatibility, and `auth_mode`. `mcp.json` declares one remote HTTPS or local fixed-runtime server. `cli.json` declares the managed runtime, executable, structured lifecycle argv arrays, status matching, authorization-domain allowlist, reviewed capabilities, and optional resource limits. A CLI package may carry `cli-bundle.tgz`; its executable path, expanded tar contents, mode bits, and SHA-256 are verified before object storage. No manifest accepts a shell command string.

## Lifecycle

Connector Revision, Installation, and Authorization are separate state machines. The active revision is changed only after validation. An invocation requires an available revision, an installed package, an active authorization when the package requires one, current policy, and passed Conformance evidence for the exact CLI bundle SHA-256 and selected Runtime RepoDigest. The manifest's declared digest is required for staging; a different Runtime is allowed only when that exact bundle also has passed Conformance evidence for its RepoDigest. Managed CLI packages are projected into the same catalog as legacy definitions, but selection freezes the verified bundle, capability policy, runtime digest, and installation authorization. Legacy CLI definitions retain definition-scoped Conformance lookup; managed packages use bundle-scoped lookup because their Installation ID differs from the definition that produced the evidence. Disablement and revocation fail closed before a new external process or request is started. CLI credentials are materialized only for one broker command: provider-owned packages receive `CONNECTOR_CREDENTIALS_JSON`; the reviewed DingTalk CLI receives only a short-lived token in `AGENT_PLATFORM_DWS_ACCESS_TOKEN`, while its rotating refresh token remains in platform-encrypted storage. Broker output is redacted before it crosses the Runtime boundary. MCP HTTP targets are checked against the declared Egress host list during materialization and isolated tests.

For a selected managed CLI Connector, the execution snapshot also freezes the package object key and SHA-256. The Worker verifies that exact package, mounts its bundled `skills/*/SKILL.md` files read-only, and points the Runtime at a Connector-specific Skill before any CLI call. The official Feishu package includes a router Skill and all 28 upstream Skill entry points from the pinned CLI version, with their references; the older built-in Feishu CLI Definition mounts the same resources. The root router and common reviewed flows are loaded into the initial Runtime instruction. Selection supplies usage instructions; it never bypasses the broker's capability, authorization, scope, or approval policy.

P1 adds a platform Publication projection above immutable revisions. A Publication selects one active revision for a package source and records its available or disabled state, the Administrator that changed it, an optimistic version, and update time. Publications never own User credentials. A User Installation selects one published revision and one current Authorization while retaining other account Authorizations for explicit selection. Creating or selecting another Authorization does not revoke the remaining accounts; disconnect and revocation operate on the targeted Authorization and clear the selected reference only when it points to that record.

CLI package manifests may select only a built-in authentication driver: `none`, `connector_package`, or `feishu`. Packages without the field retain the P0 derivation from `auth_mode`. The Feishu driver is platform code and cannot be supplied by a package.

## Result and audit boundary

The execution plane returns `{ok,data,request_id,warnings}` on success and `{ok:false,error:{type,message,retryable,next_action},request_id}` on failure. It redacts exact credential bytes before persistence. For a migrated Feishu installation, Runtime credential materialization uses the same owner-scoped provider-application lookup as account authorization, including its legacy application fallback when the new projection is absent; an active access token alone is insufficient for the official CLI. A Session or Run command that actually lacks the selected User scopes offers the managed Feishu authorization flow and a direct action link in its composer. Audit records contain actor, Connector, revision, mode, operation, risk, identity reference, timing, outcome, error type, request ID, policy revision, and approval reference. They never contain tokens, secrets, authorization URLs, raw stdout/stderr, full arguments, or business results.

## Migration

Migration `000042_connector_packages.sql` creates package, revision, installation, authorization, and audit projections without deleting existing MCP/CLI tables. Migration `000043_connector_package_backfill.sql` maps existing tested MCP servers and enabled CLI definitions to synthetic revisions marked `legacy_projection`; these rows preserve identity and audit continuity but are excluded from the managed runtime catalog. New writes use the unified seam; old snapshot columns remain readable until all historical consumers are migrated.

Migration `000054_connector_package_publications.sql` adds the Administrator-owned Publication projection and indexes installation authorization state. It does not publish a synthetic legacy projection or delete old CLI records. Migration `000055_connector_feishu_authorization.sql` adds installation-oriented Feishu setup and OAuth flows, external account identity, refresh material, and one reusable provider application per User. Migration `000056_feishu_connector_installation_projection.sql` installs an idempotent publication trigger: once an Administrator publishes a non-synthetic `feishu` revision, it projects enabled Users, encrypted application identity, active unexpired account and refresh tokens, and future Expert bindings into the unified model. The trigger also covers a publication created after the migration has already run. Historical snapshots and every legacy table remain unchanged.

The public catalog lists only active Publications and never starts setup while browsing. Installation is idempotent by User and package source. Feishu authorization keeps multiple external accounts isolated under one Installation, selects one for execution, rotates access and refresh tokens with optimistic version checks, and clears both credential forms on disconnect. Administrator publication responses and health counters expose exact package, bundle, and Runtime Digests without object keys, credentials, external identities, scopes, or provider payloads. Immediately before a managed command, the Worker revalidates publication state, installation ownership/state, the frozen revision, frozen selected authorization, scope policy, Runtime Digest, and one-use approval; upgrading an installation does not rewrite an already-frozen snapshot.

DingTalk's managed CLI authorization uses the pinned device flow. Its token exchange may omit a refresh token, in which case the grant expires with the access token. If the token omits a User ID, the adapter reads the contact profile, including `orgUserId`; a single contact result without `corpId` is accepted only when the OAuth organization is unambiguous. An unavailable contact profile retains an organization-scoped grant bound to the OAuth `corpId`, while an explicit conflicting organization is rejected. The organization CLI access check remains mandatory. After an approved device code is exchanged, any completion failure ends that flow because the code is single-use; the User must start a new flow after resolving the cause. Provider CLI denials distinguish enterprise, User scope, channel, and expired-auth categories without exposing credentials; transient errors before approval remain retryable.

`BuildOfficialFeishuArchive` is the only official Feishu package assembler. It accepts the exact reviewed `@larksuite/cli` bundle and exact Runtime RepoDigest after the existing isolated builder and Conformance ports succeed, adds the reviewed policy, router Skill, and pinned upstream reference archive, and passes the shared package parser before an Administrator can stage it. The Connector package revision can advance independently of the reviewed CLI version; the Skill references remain pinned to that CLI version. The upstream references are read-only command documentation; they do not generate or expand the manifest's capability allowlist. The reference archive is accepted only for its matching CLI version and reviewed SHA-256. Staging also requires a passed `cli_connector_conformance` record for the exact bundle SHA-256 and Runtime RepoDigest. Missing or merely claimed evidence fails closed.

The pinned `@larksuite/cli@1.0.93` source (`larksuite/cli` tag `v1.0.93`, commit `2aebe8970f0a472dfc864b6ac3d19d080e75041f`) defines 527 shortcuts. The official package has a static, SHA-256-pinned policy for its 523 User-capable shortcuts, including `docs +create`, `docs +fetch`, `docs +update`, `contact +search-user`, and `task +create`. Four Bot-only shortcuts and unrestricted raw OpenAPI calls are outside this revision. Upstream Skill references remain documentation; the matching `capabilities.json` and `cli.json` are the reviewed execution boundary. Each shortcut carries its command prefix, User scopes, risk class, Egress, and timeout. User write shortcuts require one-use approval. The package's `activation_scopes` are a validated subset of reviewed scopes for common message, contact, task, and cloud-document operations; the remaining domains are authorized on demand for the requested capability. A managed revision receives only capabilities in its frozen `cli.json`; changing this source does not mutate an installed revision or existing authorization. An Administrator must stage and publish a new package with exact bundle/Runtime Conformance, the User must upgrade the Installation, and a User whose selected authorization lacks an operation's scopes must authorize again. The Worker checks the selected authorization against the invoked capability before releasing credentials or requesting approval. Bundle-level Conformance does not establish that every upstream API endpoint succeeds for a specific Feishu tenant and grant.
