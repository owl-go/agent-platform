# Teambition

使用 `teambition-cli`（等价别名 `teambition`）。CLI `0.3+` 从 Remote MCP2
动态取得命令、Schema 和文档。参数以当前叶子 Help 为准，企业配置以实际查询为准，权限以
服务端执行结果为准；目录中出现能力不代表当前身份已获准执行。本 Skill 保留跨命令编排和业务规则。

## 使用约定

- 使用现有 CLI 和已提供的调用上下文。本技能处理业务操作，不管理 CLI 安装、升级、登录方式或凭据。
- 不读取、输出或保存凭据，不通过参数或改写配置切换授权身份。
- 根据可信上下文和工具结果区分对话用户、CLI 当前身份与业务目标人员。`user me` 返回 CLI 当前身份，
  不用它覆盖上下文已明确的目标；“我 / 我的”按已确认的当前用户解析，目标不明确时才询问。

## 按需读取 CLI 文档

已知命令时直接读取叶子 Help；路径不明时从相关分组逐级发现，不猜命令或 flag：

```bash
teambition-cli <domain> --help
teambition-cli <domain> <subgroup> <action> --help
```

不熟悉能力、多步流程或 TQL 时，通过 CLI 搜索服务端文档，再读取最相关的路径：

```bash
teambition-cli tools call teambition.docs.search --arguments-json '{"query":"要完成的业务目标","limit":5}' --json
teambition-cli tools call teambition.docs.get --arguments-json '{"path":"搜索返回的path"}' --json
```

- 按文档返回的 `cliPath` 定位命令，再用叶子 Help 核对必填项、类型、默认值和互斥约束。
  Schema 或返回字段不清楚时，用 `tools describe <文档返回的Tool名称> --json`。
- `tools call` 的常规用途仅限上述两个只读文档工具；业务操作走公开 CLI 命令，不以原始调用
  绕过缺失命令、参数约束或权限。用户明确要求的协议诊断另行处理。
- 本轮已核对且契约未变的文档可复用，不要求每步扫描全部目录。文档服务不可用时可用已有
  Help 和本地参考；仍缺少必要依据时说明阻塞，不试执行写命令猜语法。

## 解析目标与参数

组合请求先确定每步的目标、条件、读写性质和输入输出依赖。只读解析完成后再写入；相互独立的
只读步骤可并行，下游必须等待上游成功。用于后续绑定的响应使用 `--json`。

### 查询模式与范围

1. 精确 ID 优先；查询子对象使用 Help 提供的父对象模式；多条件筛选使用 TQL/搜索模式。
   每步选择一个目标模式，分页、排序、补全可按 Help 组合；不假设不同模式会自动求交集。
2. 保留当前项目和用户指定范围。当前项目内查询优先使用项目查询入口；企业级 TQL 不会自动
   继承项目范围，不能因查询失败而删除项目或人员条件。
3. 参数保留用户明确值和来源；冲突不以后写覆盖处理。缺少值时用可信上下文或只读查询补齐，
   默认值仅在用户未指定时使用；无法可靠确定时再询问。

### 名称解析与结果绑定

项目名、姓名、任务名分别从 `project`、`member`、`task` 的只读查询解析。当前 CLI 企业可从
`user me --json` 核对；不得替换上下文限定的企业。状态、任务类型、标签、优先级依赖企业/项目配置，
先解析所需上下文，再查询实际配置，不能用示例值或固定数字含义替代。

1. 从 JSON 响应提取真实字段，绑定来源、名称、ID 和资源类型；不从展示文本猜 ID，不用同名对象替换。
2. 分页结果先取齐消歧所需页面：0 条停止该目标，多条用只读条件收敛或请用户选择，唯一时才绑定。
3. 空值、缺失字段或类型不符时停止下游；写操作产生的 ID 还要确认实际成功后才能使用。

创建任务但未指定项目时，优先使用上下文已明确的目标项目；没有项目上下文时再查询候选项目。
只有一个候选时自动绑定并告知用户；多个候选时让用户选择。

## TQL 与任务查询

先读相关 CLI Help/指南；服务端未完整覆盖语法时，任务查询读取 [任务 TQL](references/tql.md)，
项目查询读取 [项目 TQL](references/project-tql.md)。保留这两份参考作为字段、运算符、时间函数和
构造规则的依据；其中的默认约定不覆盖当前 CLI 明确的契约或用户指定范围。

自然语言条件先分成可直接翻译、需要解析为 ID 和暂不可表达的谓词，再拼装与校验。用户给出完整
TQL 时保留其原意；无法表达的条件不得静默丢弃，应说明限制。使用 `me()` 前确认它代表
的 CLI 身份与用户意图一致；不一致时使用已核实的目标 TB userId。


### 归档（回收站）任务的默认范围

查询任务默认只返回未归档任务，不要把回收站中的任务混入正常结果：

1. 普通 TQL 查询按参考加入 `isArchived = false`，已有显式归档条件时不再追加；CLI 默认范围和
   `--include-archived` 的适用模式以当前 Help 为准，不与用户给定的 TQL 冲突。
2. 只有用户明确要求包含回收站/归档任务时才扩大范围；泛指“所有任务”不构成明确要求。
3. 只查归档任务使用 `isArchived = true`；当前 Help 允许显式 TQL 省略 `--include-archived` 时无需重复传入。
4. 展示包含归档任务的结果时，必须逐条标注归档状态，不能让用户把回收站任务误认为在办任务。
5. 统计、风险分析和批量写操作一律基于未归档结果；若用户要求纳入归档任务，须先说明该影响。

## 按依赖顺序执行

执行前按叶子 Help 核对必填项、查询模式、参数类型和冲突；不自行补造约束，不回退到旧 OpenAPI。

写操作顺序根据资源依赖和目标上下文确定，不照搬用户自然语言中的词序：

1. 先创建或解析容器、成员和其他前置资源，再操作依赖它们的对象。
2. 先执行上下文变更，再执行依赖新上下文配置的更新。例如跨项目移动任务后，再按目标项目配置
   更新状态、任务类型、标签或执行人。
3. 两端对象均存在且已确认后，再创建关联或依赖关系；删除、解除关系和清理旧资源放在依赖它们的
   操作完成后。
4. 同一对象的多步写操作串行执行；某个写步骤失败时停止其下游步骤。批量高影响操作默认
   fail-fast，首个失败后停止剩余写入，只有用户明确要求继续时才处理互不依赖的其他对象。
5. 不假设存在事务或可靠回滚，不自动撤销或重放已成功的写操作；超时或结果未知时先核查是否生效。
6. 每个逻辑写入组完成后用只读命令验证实际状态，并分类记录成功、失败和未执行对象。

- 创建项目默认直接创建；只有用户明确指定模板时才使用模板创建动作。
- CLI 报项目必填字段缺失时，向用户收集缺失字段后重试。
- 分页以响应中的 `nextPageToken` 是否为空为结束条件；token 值未变化不代表已结束。
- `--json` 用于后续还要解析、关联或补全数据的组合流程；最终是否直接展示 JSON 由用户决定。

Skill 不自行判断用户是否有项目或任务权限，也不复制后端权限规则；权限结果以服务端为准，不绕过权限。

## 高影响操作

执行删除、移动、替换成员或标签、解除依赖等不可逆或影响较大的操作前：

1. 查询当前状态并形成快照，绑定精确目标 ID、数量和关键字段。
2. 展示预期变更后的状态、关键参数和影响范围。
3. 遵守当前确认要求；已有针对同一目标、参数和范围的明确授权可复用，不重复询问。
   尚未明确授权具体影响时，先确认再执行。
4. 用户修改目标、范围、顺序或参数时，原确认失效；重新解析、校验和确认。
5. 目标来自动态查询时，写入前重新核对目标 ID 集合；集合变化时展示差异并重新确认。

## 领域编排规则

### Teambition 与钉钉映射

用户要求通知任务执行人/参与者或关联项目群时，先从 TB 业务对象取得目标 ID，再读取
`teambition-cli dingtalk --help` 和对应叶子 Help，或搜索 `dingtalk/bridge` 指南。
已知 TB userId 时使用 `user-to-dingtalk`，不退回姓名匹配，也不把员工工号当成映射结果。
返回的 `dingtalkUserId` 是企业内 staffId，不是 openDingTalkId；ID 保持字符串，不与企业 ID、
操作者或其他人员的 ID 混用。缺失映射不代表用户不存在；多结果须匹配请求中的目标 ID。
本技能负责 TB 侧已有映射的查询与交接，后续钉钉操作遵循外部能力的文档，不在这里维护其命令。

### 任务依赖

- `from-task-id` 是前置任务，`to-task-id` 是后置任务。
- 用户说“A 依赖 B”时，B 是前置任务，A 是后置任务。
- 自然语言方向不明确时，先展示前置和后置任务并确认。
- 未指定依赖类型时推荐 `F->S`，但创建前必须展示最终方向和类型。
- 查询依赖后，收集 `fromId` 和 `toId`，查询任务详情补全两端任务名称后再展示。
- 删除前先查询并展示依赖 ID、两端任务和依赖类型，再确认删除。

### 项目角色及成员

用户要求“项目所有角色及对应成员”时：

1. 查询全部角色和全部成员；“所有角色”包含隐藏角色，用户只说“角色”时不默认包含隐藏角色。
2. 用 `role.id` 与 `member.roleIds[]` 关联，多角色成员出现在每个对应角色下。
3. `roleIds` 为空时，用 `member.role` 匹配 `isDefaultRole=true` 且 level 相同的角色。
4. 空角色也必须保留。

### 标签

按名称更新任务标签前，必须先确认项目标签查询可用。若标签查询返回 403
`UserTokenNotAllowed`，禁止继续使用名称模式，以免清空原有标签；提示用户提供标签 ID。

### 项目封面

项目封面必须使用长期可访问、且不含临时签名参数的 HTTP(S) 图片 URL。CLI 上传接口返回的临时
`downloadUrl` 不得用作封面。本地图片无法直接作为封面时，提示用户提供稳定在线 URL。

### 文件

查询文件详情、预览或下载链接时，从目标命令的 `--help` 查找签名链接相关 flag；帮助中存在该
flag 时必须启用。其中 `project file-detail-query` 必须传 `--need-sign`；不传时响应不包含
`downloadUrl` 和 `previewUrl`，属于静默缺失，不得据此向用户宣称文件没有下载链接。签名 URL 有
有效期，不得描述为永久链接。

### 工作流

任务可流转状态结果如果只有 taskflowId，应继续查询项目工作流列表并补全工作流名称。展示工作流
时同时保留名称和 workflow/taskflow ID；权限不足时仅展示 ID 并说明限制。

### 工时

工时命令的身份类参数（`--submitter-id`、`--user-id`、`--operator-id`、`--subscriber-id` 等）
必须来自可信来源，禁止编造、硬编码或从历史对话中复用：

1. 提交人/操作人（`--submitter-id`、`--operator-id`、`--subscriber-id`）一律为当前登录用户：
   先执行 `teambition-cli user me --json`，从响应的 `userId` 字段绑定；禁止跳过该查询直接填报。
2. 工时执行人（`--user-id`）根据用户意图确定，未指定时为已确认的当前用户；姓名通过 `member`
   查询解析唯一 userId。对话用户与 CLI 身份不一致时，不把 CLI 身份当作填报目标；核对当前命令
   是否允许为该目标填报，不用业务参数切换授权身份。
3. 这些 ID 只是业务参数，不改变服务端鉴权主体；填入错误 ID 时 CLI 可能照常成功执行（静默失败），
   因此执行前必须核对上述绑定来源。

## 展示规则

- API 的任务 `content` 字段展示为“标题”，不展示为“内容”。
- 隐藏缺失、null、空字符串和空数组字段；`0` 与 `false` 是有效值，有明确业务含义时必须展示。
- 单个任务默认用段落展示；多个任务默认用表格展示：标题、状态、优先级、执行人、截止时间。
- 结果包含子任务时增加“父任务”列，格式为 `任务名称（#编号）`。
- 按本次展示需要使用字段选择或 `--enrich-fields` 补全名称，不强制每次传 `all`；批量补全优先于
  逐个查询。仍无法补全的名称标为未知，不猜测。
- 展示项目角色及成员时保留角色 ID 和成员 userId，避免重名造成歧义。
- 优先级名称以企业配置为准，不使用固定数字含义替代企业配置。
- 时区、对象标签和链接格式优先遵循用户或上下文约定；未指定时按北京时间（UTC+8）展示。
- 未约定对象展示格式时，任务和项目 ID 渲染为链接：
  - 任务：`https://www.teambition.com/task/{taskId}`
  - 项目：`https://www.teambition.com/project/{projectId}`

## 错误恢复

先定位失败的计划步骤，停止依赖它的下游步骤；互不依赖的只读步骤可以继续。然后按类型恢复：

1. 参数错误：回到模式选择与执行前复核，按最新动作 Help 修正。
2. TQL 错误：回到谓词拆分和拼装顺序重新构造，不删除出错条件后重试。
3. 命令缺失或目录过期：读取相关 Help；必要时 `teambition-cli tools list --refresh --json` 刷新一次
   再核对。离线缓存不证明最新能力；仍不存在时报告能力或路由不可用，不直接归因为缺少权限。
4. 认证或授权错误：按 CLI 返回的明确恢复指引处理，不自行推断登录方式或改写凭据。
   已发起授权交互时等待结果，不重复启动；没有恢复入口或用户拒绝时报告阻塞。
   恢复后确认身份和目标未变，再继续未执行的步骤；写操作结果未知时先核查是否已生效。
5. `AUTH_SCOPE_REQUIRED`、普通 403、业务校验失败和网络错误按实际错误分别处理，
   不把所有失败都转成登录或写入重试。
6. 404 先核对目标 ID、范围和实际错误，不能仅凭状态码断言对象不存在；写失败报告已成功、失败和
   未执行的步骤。诊断可用离线 `doctor`，不自动改写端点、`x-canary` 或配置。

### 稳定业务错误

完成迭代返回 `Has undone tasks` 表示迭代中仍有未完成任务：停止完成操作且不自动重试，先通过只读
查询展示这些任务，由用户选择完成或移出迭代；只有变更执行成功且只读复查确认不存在未完成
任务后，才重新执行完成迭代。

向用户展示错误时只保留安全、可操作的摘要。不得直接输出原始服务端响应体、认证请求头、Token
或包含敏感内部信息的 raw error；必要时可保留已脱敏的状态码、错误码和 request/trace ID。

除非用户明确要求诊断，避免使用 `--debug`。向用户展示前仍需检查输出，不得泄露 Token、授权码、
PKCE verifier、上传凭证、本地绝对路径或服务端原始敏感信息。

## 示例

用户：“查张三在电商项目里本周到期、还没完成的任务。”

四个谓词中，“执行人是张三”和“项目是电商项目”需要解析为 userId 和 projectId；“截止时间是本周”
和“任务未完成”可直接翻译为 `dueDate` 的本周范围和 `isDone = false`。据此建立三个计划步骤：

1. 从 `member --help` 定位成员查询动作并查询张三，绑定唯一 userId。
2. 从 `project --help` 定位项目查询动作并查询电商项目，绑定唯一 projectId。
3. 前两步互不依赖，可以并行；完成后按 `project task-query --help` 在目标项目内使用 TQL：

   ```text
   executorId = '<userId>' AND
   dueDate >= startOf(w) AND dueDate <= endOf(w) AND
   isDone = false AND
   isArchived = false
   ```

   将已解析的 projectId 绑定到项目查询参数。用户没有提到归档或回收站，因此不扩大到归档范围。

最后按 Help 校验并执行，按需要补全执行人、状态等名称后展示。

## 示例：创建任务（项目推断与必填字段）

用户：“在电商项目里创建一个任务：设计首页 banner。”

1. 从 `task create --help` 读取命令用途和参数，确认需要 projectId。
2. “电商项目”是名称，先执行只读解析：从 `project --help` 定位项目查询动作，查询名称含“电商”
   的项目。返回 1 条时绑定 projectId；多条时展示名称和 ID 请用户选择；0 条时停止并报告未找到。
3. 执行创建。若 CLI 返回项目必填字段缺失（如备注、优先级），列出缺失字段向用户收集后重试，
   不得自行编造必填字段的值。
4. 创建成功后，按当前展示约定呈现任务标题及对象引用或链接。

## 示例：高影响操作（移动任务）

用户：“把任务 xxx 移到产品项目。”

1. 移动是高影响操作。先查询任务当前状态形成快照：任务 ID、标题、当前项目、任务分组和列表。
2. “产品项目”是名称，执行只读解析绑定唯一 projectId。
3. 核对预期变更（任务、目标项目、跨项目移动可能重置任务列表位置），按高影响操作规则确认授权后
   执行 `task move`；目标或范围改变时重新确认。
4. 移动完成后重新查询任务验证实际所在项目和位置，再向用户报告结果。
